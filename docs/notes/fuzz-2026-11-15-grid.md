# Fuzz pass 2026-11-15: pane grid

Three findings from the grid fuzz pass (pane grid, tab strips, drag, rails, full screen, focus).

## 1. A stale focus request replayed when a pane remounts

Symptom: with two panes, a key that moves the keyboard (cmd+t, a direction key, a rail click)
leaves a focus request on one pane. After a click into the other pane, leaving full screen,
switching spaces and back, or a fold or unfold on resize or zoom moved the keyboard (and, for a
non-thread body, the pane focus) back to the first pane. A command typed next ran in the wrong
terminal.

Cause: `stores/shellView.ts` keeps one `focusRequest` (pane, seq) and never marked it served.
`OpenPane` (PaneView.tsx) and `PaneRail` focus on mount whenever the request names them, so a
remount replayed it.

Fix: `takeFocusRequest(seq, "rail" | "open")` marks a request served. Each request moves the
keyboard once. Two marks, because a rail and the open pane it unfolds to each serve the same
request once: a click on a rail's icon focuses the icon, the pane unfolds, and its active tab
must still take the keyboard. An open pane marks both, so a later fold does not replay it on the
rail either. A pane that mounts after its request (a new pane for an opened or dropped tab)
still takes it, because the request was not served yet.

Left as is: a request a rail served (a direction key onto a collapsed rail) is still served once
more by the open pane when that pane opens later. Opening a collapsed pane asks for the keyboard
anyway (collapse.ts), so this is what happens in practice.

Thread prompts already kept their own handled seq (ThreadComposer), so a thread pane was safe.
The bug showed with terminals, diffs and pages.

## 2. Many tabs cut off the active tab and the strip's controls

Symptom: once even icon-only tabs overflowed the strip, the newest (active) tab, "+", Collapse
and Full screen were clipped by the strip's `overflow-hidden` and could not be reached.

Fix: the tabs sit in their own horizontal scroller (scrollbar hidden). "+", Collapse and Full
screen sit after it in the strip, so they stay in the pane. The active tab is scrolled into view
when it changes, a tab comes or goes, or the tabs refit. The scroller has 1px of padding, offset
by a -1px margin, so a tab's focus ring at either end is not cut and the layout does not move.
When the tabs fit, the strip draws pixel for pixel as before (compared in WebKit). The fit
measuring is unchanged: it reads the strip's width as before.

Drag: autoScroll is off, so the scroller never moves during a drag. Positions measured at drag
start stay right for the visible tabs. A tab scrolled out of view keeps its off-screen place, so
a drop over the controls with tabs hidden to the right puts its insertion bar past the visible
tabs. That case is rare and was left alone.

## 3. No keyboard after a tab drop

Symptom: after dragging a tab to split a pane or into another pane, `document.activeElement`
was `<body>`. The focus border showed the new pane, but typing did nothing until a click.

Cause: the dragged tab's node, which had the keyboard, unmounted with the move, and nothing
asked the destination for the keyboard.

Fix: `runGridDrop` (shell/spaceActions.ts) runs the drop's verbs and then asks the current
space's focused pane (the one the drop focused) for the keyboard. A drop on a space tab is
unchanged, because the window stays where it was. This relies on fix 1: the request is served
once, so it is not replayed later.

## Tests

- vitest: PaneView.test.tsx covers serve-once: a remount, a fold and an unfold do not replay a
  request; a rail then the pane it unfolds to both take one; a pane mounted after its request
  takes it; a new request still focuses. spaceActions.test.ts covers runGridDrop.
