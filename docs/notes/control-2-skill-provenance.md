# Skill provenance (2026-10-22)

Every skill file the daemon ships now says which build rendered it and where that
build's source is, and the help skill sends questions about internals to that source,
so a thread asked how something works inside Code Foundry reads the real code at the
right revision instead of guessing. Daemon and skill text; no GUI or proto change.

## The line

Every SKILL.md and every reference carries one line right under its `# ` title:

```
Rendered by Code Foundry v0.21.3 (commit 844a109c0123) · source: https://github.com/alexwaumann/code-foundry/tree/v0.21.3
Rendered by Code Foundry dev (commit e10da433c060) · source: https://github.com/alexwaumann/code-foundry/tree/e10da433c060674961188296c406dda8c35021b3 (dev build: the source there may not match this build)
Rendered by Code Foundry dev (commit unknown) · source: https://github.com/alexwaumann/code-foundry (dev build, commit unknown: the source there may not match this build)
```

* `version.Info.Provenance` writes it; `version.Info.Source` gives the repo, ref and URL.
  The ref is the version when it is a release tag (`vX.Y.Z` or `vX.Y.Z-tip.N`, strict),
  else the commit with `-dirty` stripped (7 to 40 hex characters), else none (the URL is
  the repository). The text keeps `-dirty` and cuts the commit to 12 characters, like
  `code-foundry version` (whose `formatVersion` now calls the same `ShortCommit`).
* Anything that is not a release tag is called a dev build, with the caveat in the line
  itself. The help skill keys on the words `dev build`; a test ties the two together.
* The repository comes from one place: `version.Module` is this package's own import
  path (`reflect.TypeFor[Info]().PkgPath()`) minus `/internal/version`, and
  `version.SourceRepo` is `https://` plus that. A test checks it against `go.mod`.
  `version.ReleaseRepo` (where updates download from) stays separate: a fork may
  publish releases elsewhere.
* Static files place the line with a new `{{cf.provenance}}` placeholder under the title
  (15 files). Rendered references get it from `header`, which no longer puts the version
  in the "Generated by the code-foundry daemon" sentence. `reference/getting-started.md`
  is `docs/GETTING-STARTED.md` with the line inserted under its title (`underTitle`); the
  test checks exactly that.
* Ember's skill carries it too: `EmberFiles` takes `Sources` and fills placeholders like
  `Render`, and `installEmberSkill` passes `version.Get()`'s version and commit.
* The plugin skill's `example/` files carry no line: they are copied out as a new
  plugin's own files.
* `Sources` already had `Version` and `Commit`; it gained a `Provenance()` method rather
  than a field.

## The help skill's "Reading the source"

17 lines in `code-foundry-help/SKILL.md` (92 lines now, cap 120): for internals or
behaviour the references do not cover, read the source at the line's ref and never
answer from memory; WebFetch of `raw.githubusercontent.com/<owner>/<repo>/<ref>/<path>`
or `gh api 'repos/<owner>/<repo>/contents/<path>?ref=<ref>'` with the raw Accept header
(without it, a directory listing); start at `docs/ARCHITECTURE.md`, then the package it
names; cite file paths; notes and comments can be stale, so confirm in the code; and
for a dev build, say the source may not match. The URLs are templates read off the line,
so the repository is not written into the skill. The "Where to look" fallback now points
at this section before "say so rather than guess". The description gained "how it works"
(319 characters, cap 400). Nothing runs at load: the model fetches with its own tools.

## daemon.version

`--json` adds `source_url` (always) and `source_ref` (omitted when there is none), from
`version.Info.Source`. Text output unchanged; the command's description says what
`--json` adds.

## Caps

* The orchestrate and plugin SKILL.md line caps rise by two (136 to 138, 120 to 122): the
  line and its blank line are fixed overhead, not material. Ember's (under 205) had room.
* The plugin skill's 32 KiB per-file cap does not count the line (`host-api.md` and
  `primitives.md` were within 120 bytes of the cap; the line's length depends on the
  build).

## Gotcha: the wrong commit in nested worktrees

The first end-to-end run showed the main checkout's HEAD in a worktree build's line, not
the worktree's. Go stamps `vcs.revision` from the nearest enclosing repository with a
`.git` directory; a worktree under `.claude/worktrees/` inside the main checkout has a
`.git` file, so Go stamped the enclosing checkout's HEAD, and `version.Get` let the stamp
override the `-ldflags` commit `make build` sets from the worktree's own HEAD. `Get` now
prefers the build-time `Commit` when set and falls back to the stamp (a plain
`go build`). This also fixes the plugin skill's SDK pin in such builds. Release builds
were not affected (a plain checkout, both values agree).

## End to end (isolated home)

`make build` (and once `make build VERSION=v0.21.3-tip.2`), then
`CODE_FOUNDRY_HOME=/tmp/cf-prov/home bin/code-foundry daemon --dev`:

```
$ code-foundry daemon.version --json        # tip build
{"version":"v0.21.3-tip.2","commit":"e10da433…","go_version":"go1.26.10","source_url":"https://github.com/alexwaumann/code-foundry/tree/v0.21.3-tip.2","source_ref":"v0.21.3-tip.2"}
$ grep -c '^Rendered by Code Foundry' <home>/claude/.claude/skills/**/*.md   # 20 files, 1 each; 0 under example/
$ code-foundry daemon.version --json        # dev build
{"version":"dev","commit":"e10da433…","go_version":"go1.26.10","source_url":"https://github.com/alexwaumann/code-foundry/tree/e10da433…","source_ref":"e10da433…"}
```

The raw URL and `gh api` forms in the skill were checked against a pushed commit
(HTTP 200, directory listing). Ember's skill was checked by unit test only (enabling
Ember starts its thread). No live thread was asked an internals question.
